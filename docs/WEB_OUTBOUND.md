# Web 出库页面（任务 25）

## 一、页面与入口

左侧导航「出库管理」在本任务上线（不再是「待开放」），点进去就是出库单列表。

| 页面 | 路由 | 权限 | 数据来源 |
| --- | --- | --- | --- |
| 出库单列表 | `/outbound` | `products:read` | `GET /outbound-orders` |
| 新建出库单 | `/outbound/new` | `outbound:write` | `GET /warehouses` + `GET /inventory/balances` + `POST /outbound-orders` |
| 修改出库草稿 | `/outbound/:id/edit` | `outbound:write` | `GET /outbound-orders/{id}` + `PATCH /outbound-orders/{id}` |
| 出库单详情 / 确认发货 | `/outbound/:id` | `products:read` 可看，写操作看角色 | `GET /outbound-orders/{id}` + `POST /outbound-orders/{id}/ship` + `POST /outbound-orders/{id}/cancel` |

只读角色（VIEWER）能进列表与详情，页面里不出现新建/发货/取消按钮；路由守卫也拦：`/outbound/new` 与 `*/edit` 要求 `outbound:write`，否则直接跳 `/forbidden`。

## 二、列表页

列：出库单号（副标题是创建时间）、状态标签（待发货 / 已发货 / 已取消）、仓库、收件人（副标题电话）、商品摘要（`SKU 等 N 个 SKU`）、件数、出库成本、快递 / 运单号、发货时间。

筛选：搜索（出库单号 / 运单号 / 收件人 / 电话）、状态、仓库、创建日期区间，另有刷新与清除筛选。分页 10/20/50/100，底部「共 N 条 · 第 x / y 页」。

点行进入详情；右上角「新建出库单」只有 `outbound:write` 才出现。

## 三、新建 / 修改草稿

三段式表单，顺序就是实际操作顺序：

1. **发货信息**：发货仓库（默认取偏好仓库，可切）、快递公司（10 个常用编码 + 暂不指定）、发货运单号（按字符串保存，前导零不丢）、备注。
2. **客户收货信息**：收件人、联系电话、收件地址。草稿可以留空，但页面会提示「尚未填写：…；确认发货前需补齐」。
3. **商品明细**：点「添加 SKU」打开选品弹窗，弹窗查的是**当前仓库的库存余额**，每行显示可用库存与均价，选中即带入数量 1 与本仓库可用数量。

明细表每行可改发货数量：超出该行可用库存时立刻标红「超过可用库存」，并在表头下方汇总「以下 SKU 超过当前可用库存，确认发货会被服务器拒绝」。

「刷新可用库存」会按 `warehouseId + productId` 逐个回查 `GET /inventory/balances`，改仓库也会自动重查 —— 可用数量永远来自服务端，页面不做任何 `10 - 3` 的推算。

保存后跳到详情页；离开有未保存修改时会二次确认（`onBeforeRouteLeave` + `beforeunload`）。

## 四、详情页与确认发货

- 头部：单号 + 状态标签、仓库、创建人、创建时间、发货人与发货时间，右侧刷新 / 修改草稿 / 取消草稿 / 确认发货（后三个仅草稿 + 有权限时出现）。
- 四张指标卡：发货件数、出库成本（草稿时标注"预计出库成本 / 按发货时的移动平均成本计算"）、快递公司、状态。
- 客户收货信息与库存/成本两栏：收件人、电话、地址、备注、仓库、单号、发货时间、确认操作号（发货后才有）。
- 明细表：SKU、商品名、数量、单位、**实时可用库存**、成本快照（草稿为 `—`）、行成本、跳转 SKU 库存详情。

点「确认发货」弹出确认框：可改快递公司 / 运单号 / 备注（不填就用草稿里的值），并提示"库存不足会被拒绝，数量保持不变"。确认后：

```
api.ship(id, { clientOperationId, carrierCode?, trackingNo?, remark? })
  ├─ 成功 → 用返回的单据刷新页面（状态 SHIPPED、成本快照、可用库存），并提示"库存已在服务端扣减"
  └─ 失败 → 进度条之外只做两件事：把服务端文案原样显示、重新查一次可用库存
```

**库存不足时页面禁止完成发货，且显示的是服务器返回的错误**：服务端 `409 OUT_OF_STOCK` 的 `details.shortages` 被翻译成「库存不足，未扣减任何库存：GA-65W 需要 8 件、可用 7 件。请调整数量或先补货。（请求编号 …）」，单据保持 `DRAFT`，库存与流水都不变。页面不会在本地把按钮静默禁用（那样用户永远看不到具体差额），只把已知超量作为橙色提示，真正判定由发货事务做。

**幂等靠复用一个操作号**：`shipFingerprint(orderId, body)` 把单号 + 快递公司 + 运单号 + 备注拼成指纹；同一个指纹重试沿用同一个 `clientOperationId`，网络超时后再点一次不会二次扣减；改了运单号就换新操作号（否则服务端会判成"同号不同内容"409，页面也有对应文案）。

取消草稿走二次确认，成功提示"草稿已取消，库存未变动"；重复取消时服务端返回 `cancelled: false`，页面提示"此前已取消"而不是报错。

## 五、不在前端算库存

- 数量、成本、均价、可用库存、合计全部是接口字段；页面只用 `formatQuantity` / `formatMoney` / `formatUnitCost` 做展示格式化。
- 页面与客户端里没有 `stock_balances` / `stock_movements` 字样，除 `<el-input>` 的绑定外没有 `quantityOnHand = …` 这类赋值。
- 唯一的写请求是 `/outbound-orders`（POST / PATCH / ship / cancel）；`api/inventory.ts` 仍然只有 GET。
- `scripts/web-outbound.test.mjs` 用正则守住以上三条（`quantityOnHand\s*[-+*/]?=`、`stock_balances`、`Math.random` 等）。

## 六、怎么自己验证一遍

1. `pnpm db:up` → `pnpm prisma:migrate:deploy` → `pnpm start:api`，另开终端 `pnpm dev:web`。
2. 先让该仓库有货：手机扫码验收（或 `/receipts` 对应的采购流程）入库 10 件。
3. 电脑打开 http://localhost:5173/outbound → 新建出库单 → 选仓库、点「添加 SKU」选这个商品（可用库存显示 10）→ 数量填 3 → 填收件人 / 电话 / 地址 → 保存草稿。此时「商品库存」里仍是 10。
4. 在详情页点「确认发货」→ 状态变已发货，成本快照出现；回到「商品库存」看到 7 件，「库存变动流水」多一条 `出库发货 -3 10→7`，来源单据是这张出库单。
5. 再建一张 8 件的草稿并确认发货 → 页面显示服务端返回的「库存不足…需要 8 件、可用 7 件」，库存仍是 7。

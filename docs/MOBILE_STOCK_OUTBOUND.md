# 手机端库存查询与扫码出库（任务 26）

## 一、页面与入口

首页「常用操作」里的「库存查询」「扫码出库」两块从占位变成真页面，权限分别是 `products:read` 与 `outbound:write`（没有权限时卡片置灰、点击提示，并在 `onShow` 里二次拦截）。

| 页面 | 路径 | 内容 |
| --- | --- | --- |
| 库存查询 | `pages/stock/index` | 搜索框（名称 / SKU）、扫条码、仓库筛选、结果列表（数量 + 仓库 + 均价 + 待入库） |
| 库存详情 | `pages/stock/detail` | 合计现存 / 待入库 / 仓库数、各仓余额、最近 20 条库存流水 |
| 扫码出库 | `pages/outbound/index` | 选仓库 → 扫码或搜索加行 → 改数量 → 填收件与快递 → 存草稿 → 二次确认发货 → 结果 |

## 二、库存查询

**扫码**：`uni.scanCode({ scanType: ['barCode','qrCode'] })` → `findByCode()` 依次尝试三种只读查询：

1. `GET /inventory/balances?barcode=<原样条码>`（精确，前导零保留）
2. `GET /inventory/balances?sku=<原样条码>`（有的商家把条码填成了 SKU）
3. `GET /inventory/balances?search=<原样条码>`（兜底子串）

命中即停，结果标出「已按条码匹配 / 已按 SKU 匹配 / 搜索结果」。三次都没命中时，页面提示「没有找到条码为 X 的商品，如果这个商品没有登记条码，请改用手动搜索 SKU」。

**手输**：`searchStock()` 走 `?search=`，服务端按 SKU / 商品名称 / 条码做不区分大小写的子串匹配。

**去重**：复用已有的 `ScanGuard`——查询未结束时再扫直接忽略；同一条码 3 秒内重复上报只提示一次，避免扫码枪或手抖连发把接口打满。

结果按仓库分组，每行显示数量（0 件灰色、小于 5 件琥珀色）、SKU、单位、条码、均价、待入库、最近入库时间。点行进详情：合计现存 / 待入库 / 仓库数三张卡、各仓库的规格/条码/均价/账面成本/待入库/最近入库，以及最近 20 条流水（类型、数量变动、操作前后、来源单据、操作人、备注）。

## 三、扫码出库

1. **选仓库**：`GET /warehouses`，默认第一个启用仓库；换仓库会把已加行的可用数量清零并重新查，避免拿 A 仓的数去发 B 仓的货。
2. **扫码加行**：扫码 → `findByCode()`（带 `warehouseId`）→ 取该仓库那一行；`addOrIncrementLine()` 把同一商品合并成一行并 `+1`。**这一步只改内存里的数组，没有任何写请求**，所以重复扫码只会让"待发数量"变大，数据库库存不变。扫到别的仓库才有的商品会明确提示，不偷偷切仓库。
3. **没有条码**：扫不到就自动打开手动搜索面板（也可以直接点「没有条码？手动搜索 SKU」），输入名称 / SKU 后从结果里「加入」。
4. **改数量**：`− / 输入框 / +`，只接受 1–2147483647 的整数；超过该行上次查到的可用数量会标红「超过可用库存」。
5. **客户与快递**：收件人、电话、地址（发货必填）、快递公司（10 个常用编码的 picker）、运单号（前导零原样保存）、备注。
6. **创建草稿**：`POST /outbound-orders`，成功后页面显示单号、件数、成本，并明确写「草稿不会改动库存」。改过内容（加行、改数量、改资料）会标记草稿过期，未保存前「确认发货」不可点。
7. **二次确认**：`uni.showModal` 列出仓库、每个 SKU 的件数、收件人、快递，确认后才调用 `POST /outbound-orders/{id}/ship`。
8. **结果**：成功页显示出库单号、件数、成本、发货时间、逐 SKU 的最新余额，并说明「库存已在服务端扣减」；Web 端刷新出库管理与商品库存看到同一笔。

**库存不足**：本地先用上次查到的可用数量挡住（`overStockLines`），弹窗写清"SKU 发 N 件、可用 M 件，请减少数量并保存草稿"。如果并发导致服务端仍判定不足，`409 OUT_OF_STOCK` 的 `details.shortages` 会逐 SKU 显示"需要 X、可用 Y"，并自动重查可用数量。两种路径都不会扣库存。

## 四、失败时怎么保证不重复扣库存

`OutboundShipSubmitting`（`services/outbound.ts`）是一个带本地存储的幂等闸门：

| 情况 | 操作号 | 结果 |
| --- | --- | --- |
| 网络中断 / 5xx / 结果未知 | **保留**，下次重试复用同一 `clientOperationId` | 服务端唯一键 + 请求指纹保证只扣一次；重放返回原单据，页面提示"重试命中同一出库单" |
| App 被杀掉后重开 | 记录已落盘（`caicang.mobile.outbound-pending.v1`），仍复用 | 同上 |
| 库存不足 / 状态冲突 / 参数错误（4xx 且明确未扣） | **丢弃**，改完再发就是新操作 | 避免把"新请求"伪装成旧重试被判 409 |
| 发货成功 | 丢弃 | — |

指纹是 `[出库单 id, 快递公司, 运单号, 备注]`（单号小写、字段 trim）。改了运单号就是另一次发货，必须换新操作号——这与服务端 `confirm_request_hash` 的口径一致。

## 五、前端不碰库存

- 页面上没有任何 `stock_balances` / `stock_movements` 字符串，也没有 `quantityOnHand = …` 的赋值；数量、成本、均价全部来自接口。
- 唯一的写请求是 `POST /outbound-orders`、`PATCH /outbound-orders/{id}`、`POST …/ship`；库存查询只有 GET。
- 待发数量是本地草稿状态，清楚标注"数量只存在本页，未提交前不会影响任何仓库库存"。

## 六、怎么自己验证一遍

1. `pnpm db:up` → `pnpm prisma:migrate:deploy` → `pnpm start:api`。
2. 先在 Web 端让某个仓库有货（采购 → 下单 → 手机扫码入库 10 件），并给商品登记条码。
3. 手机 App（或 `pnpm dev:mobile` 的 H5，H5 没有摄像头，用手动搜索）：
   - 首页「库存查询」→ 扫条码 → 看到该商品在该仓库的 10 件；点进详情能看到入库流水。
   - 首页「扫码出库」→ 选仓库 → 扫同一件商品两次（待发数量变 2）→ 改成 3 → 填收件人与电话地址 → 选顺丰 → 保存草稿（回 Web 端看库存仍是 10）→ 确认发货 → 成功页显示 3 件。
4. 回 Web 端「商品库存」看到 7 件、「库存变动流水」多一条 `出库发货 -3 10→7`。
5. 再在手机建一张 8 件的单：本地就会提示"可用 7 件"；如果绕过本地检查（例如并发），服务端仍会返回"需要 8 件、可用 7 件"，库存不变。

## 七、边界

- **真机验收未做**：本任务的测试跑在 H5 构建 + 真实 API 上（扫码用输入模拟），摄像头、`uni.scanCode`、App 权限弹窗需要真机确认；打包方式见 README 的 `pnpm build:mobile:lan`。
- **不支持部分发货**：一张单要么全发要么不发。
- **出库单不能取消**：手机端没有取消入口（Web 端草稿可取消），出库单号一旦生成只能发货。
- **扫码只识别已登记条码**：条码没登记时只能手输名称 / SKU。

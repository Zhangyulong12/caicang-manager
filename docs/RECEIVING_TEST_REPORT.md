# 任务 18 报告 — 验收入库安全专项测试

## 一、结论

任务 17 的入库事务在真实 PostgreSQL 上通过了 12 个指定场景的破坏性验证，**未发现产品缺陷**。

- 专项测试 `scripts/receiving-safety.test.mjs`：**13 个子测试全部通过**（12 个指定场景 + 1 个全局一致性收口）。
- 全仓 `pnpm test`：**492 通过 / 0 失败**（任务 17 结束时为 477，新增 15 个测试节点）。
- 每次入库后都做账本对账：收货单、收货明细、库存余额、库存流水四者的数量与金额必须互相闭合，测试不依赖接口返回值自证。

执行过程中出现过 1 次失败，是测试夹具写错而非产品缺陷，详见第五节。

## 二、测试环境与方法

| 项目 | 做法 |
| --- | --- |
| 数据库 | 每次运行新建隔离库 `caicang_test_<uuid>`，`prisma migrate deploy` 建全部表，结束即删 |
| 服务 | 编译后的真实 NestJS 进程（`apps/api/dist/main.js`）监听随机端口，不用 mock、不注入 service |
| 输入 | 全部走 HTTP `POST /api/v1/receipts`，与手机端将来调用的是同一个端点 |
| 核对 | 断言直接查 PostgreSQL：`receipts`、`receipt_items`、`stock_balances`、`stock_movements`、`audit_logs`、`packages`、`purchase_orders` |
| 故障注入 | 用数据库触发器在事务中途抛异常（`RAISE EXCEPTION`），制造真实的写入失败，而不是打桩 |
| 并发 | `Promise.all` 同时发出请求，让数据库锁决定胜负 |

开发库全程只读：测试结束复核为 6 商家 / 10 用户 / 9 商品 / 2 采购单 / 0 包裹 / 0 收货单 / 0 库存行 / 0 流水，与任务前一致。

## 四、对账口径（每个场景结束都执行）

测试里的 `assertLedger()` 不信任接口自报的数字，直接从库里算：

1. **余额 = 流水合计**：每行 `stock_balances` 的 `quantity_on_hand` 与 `total_cost`，必须等于同仓库同商品 `stock_movements` 的 `SUM(quantity_delta)` 与 `SUM(cost_delta)`；且不允许出现"有流水没有余额行"。
2. **明细 ↔ 流水 1:1**：每条 `receipt_items` 必须有一条 `source_type='RECEIPT'`、`source_item_id` 指向它的流水，数量相等，成本增量等于 `landed_unit_cost × quantity`；反向不允许有孤儿收货流水。
3. **流水链条无缺口**：同一商品的流水按 `quantity_before` 排序后必须从 0 开始首尾相接（`0→6→10` 这种），这同时证明并发下没有两笔请求读到同一个起点（丢失更新会立刻表现为起点重复）。
4. **单行不超收**：`SUM(receipt_items.quantity)` 按采购行聚合后不得超过 `purchase_order_items.quantity`。
5. **状态自洽**：采购单 `RECEIVED` 必须全行收满，`PARTIAL_RECEIVED` 必须介于 0 与订购量之间，`PLACED`/`CANCELLED` 必须零收货。

数据库本身还有 `ck_stock_movements_7/8`（`before + delta = after`，数量与成本各一条）、`ck_stock_balances_1`（不允许负库存）作为兜底，测试同时验证这些约束没有被绕过。

## 五、唯一一次失败与修复

首次运行时场景 6 构造了两箱各"预计 6 件"去收一张 10 件的采购单，绑第二个包裹时接口返回：

```
409 PACKAGE_EXPECTED_QTY_EXCEEDED  全部包裹预计数量超过采购明细数量
```

这**不是缺陷**——它证明任务 16 的包裹计划约束在生效（所有包裹预计数量之和不得超过采购数量），是我的夹具与业务规则冲突。修复方式：第一箱保留计划 6 件，第二箱改为**无计划包裹**（`expectedItems` 省略），这样只有采购数量能拦住它，正好命中要测的"整单累计不超收"分支；并发版本同样改用两个无计划包裹。

修复后该场景连续通过，并额外覆盖到"无计划包裹也能被整单余量正确限制"这一点。

## 七、测试自身的边界

- **故障注入是数据库层异常，不是硬件故障**：场景 7/10 用触发器在事务中途抛错，验证的是"PostgreSQL 事务回滚是否完整"，没有模拟断电、连接中断或进程被杀。连接中断属于另一类问题（客户端重试 + 幂等键），不在本次范围。
- **同一商家的写请求在数据库层面是串行的**：`TenantContextService` 在写事务开头就 `SELECT ... FROM tenants FOR UPDATE`，所以同一商家的两次收货不会真正并行执行，而是排队。测试观察到的"只有一笔成功"来自这个串行化加上包裹/数量校验；库存余额行锁（按 `product_id` 排序）是第二道防线，防止将来出现绕过租户锁的写路径。这一点写在这里，避免夸大"行锁解决了并发"。
- **`PACKAGE_MOVED` 分支仍未覆盖**：需要精确控制"等待锁期间被改绑"的交错，现有框架无法稳定复现，与任务 17 的结论一致。
- **未做手机端/浏览器验收**：本任务不产出界面，手机扫码页面尚未开发。
- **未覆盖出库、盘点、库存查询**：这些功能还不存在，库存正确性目前只有入库一个来源。
- 隔离库在结束时删除，开发库未被写入。

## 八、结论

12 个场景全部按预期通过，收货单、库存余额、库存流水在每次操作后都互相闭合，重复提交、并发扫码、跨商家、取消订单、事务中途失败都不会污染库存。
